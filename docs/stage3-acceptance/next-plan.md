## 2. 跳过阻塞项的原则

1. **只做不依赖客户数据/法务确认的部分**；涉及客户数据的只做“到位即可跑”的准备（脚本、配置、清单、验收记录）。
2. **合成数据只用于回归和演练**，输出必须标明“基线/演练，不是验收”，不得据此宣布任何一类通过。
3. **阻塞项保持 blocked**，不因为它不挡别的开发就改状态、不写“通过”。
4. **一个增量一个 PR**，独立验证、可回滚；不改既有规则判定，除非任务明确。
5. **门禁先于进度**：3 类报告 + 20–30 份 + 客户签字，缺一项就不宣布阶段 3 通过。

## 3. 可继续开发的任务（按优先级）

### T301 · 阶段 3 验收自动化（本轮交付，不依赖客户数据）

- **问题**：现在验收靠人工按 `templates/acceptance-record.md` 逐份填、手工汇总指标；20–30 份 × 十余条规则，易错、不可复现，也无法在数据到位后当天出结论。
- **做什么**：新增 `p0/eval/stage3_acceptance.py`：
  - 读 `templates/data-manifest.csv` 同列定义的数据清单与客户金标准（期望判定、期望 fail 规则、case_kind、A/B/C 分类）；
  - 逐份解析 docx/pdf 并跑主审核链路（R01–R11 + X01–X04 + P01–P08 + D01–D10，语义按 D5 开关）；
  - 按 `README.md` §3.2 计算报告级准确率、finding 召回、关键规则召回、模板分类、干净报告误报、耗时、缺数据沉默通过、视觉项冒充通过；
  - 输出 `docs/stage3-acceptance/acceptance-<日期>.md`（逐份记录 + 3 类汇总 + 门禁核对）与 JSON；
  - 数据缺失时输出 `blocked`、列出缺口，不生成虚假指标。
- **验收标准**：
  - 单测覆盖清单校验、TP/FP/FN 与召回/准确率、门禁判定、缺数据 blocked、干净报告误报；
  - 无客户数据时退出码非 0 且汇总写明缺口；
  - 不改变生产审核 API 与既有规则判定（`pytest p0/tests -q` 全绿）。
- **涉及**：`p0/eval/stage3_acceptance.py`、`p0/tests/test_stage3_acceptance.py`、`docs/stage3-acceptance/README.md`（使用方式）。

### T302 · 验收链路演练（依赖 T301，本地样例）

- **做什么**：用 12 份草稿 + POC 标注跑一遍 T301，验证“清单 → 审核 → 指标 → 记录”整条链路；结果标“回归基线，不是验收”。
- **验收标准**：每份草稿的 fail 集合与 `eval/stage1-report.json` 一致；不产生 3 类通过结论；命令写入文档。
- **状态**：待本地挂载 `samples/byd` 后执行；CI 无样例时跳过。

### T303 · 报告审核规模化（不依赖客户数据）

- **现状**：批量审核在当前请求内顺序执行；审核历史 UI 只取最近 20 条；无分页控件；历史保留期未定。
- **做什么**：历史分页与保留期；批量审核接 P1-2 任务队列（`P0_TASKS_ENABLED=1` 时返回 202 + 任务进度）。
- **验收标准**：分页/保留单测；大批量走队列不阻塞 `/health`；单份审核结论不变。
- **涉及**：`p0/app/main.py`、`p0/app/report_store.py`、`p0/static/`、`p0/tests/`。
