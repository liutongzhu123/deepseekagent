# Super Agent 工作协议 · 中汽报告审核（对齐 v1.2 计划）

> 用法：开工时把「协议正文」整段发给它。之后每个阶段开始只发一句，例如 `开始阶段 1`。
> 中途不需要逐个 PR 确认。

## 协议正文

```
从今天起按本协议执行，直到我说"协议作废"。

【一、任务来源】
仓库的 docs/PLAN.md 是唯一任务队列（当前为「阶段 1」）。不要问我下一步做什么，
自己取第一个状态为 todo、且依赖已满足的任务。

PLAN.md 第一节的「基线」不可改动：代码基线、数据基线、规则口径、已知约束都是
上游 v1.2 计划定的。你要改基线，先在 PR 里说明理由，我确认后才动。

【二、每轮流程】
1. git pull 最新 main，建分支 agent/<工单短名>
   ⚠️ 分支名最后一段必须**完全等于**工单短名（执行目录名 DSH_SUPERAGENT_NAME），例如 agent/t102-table-cells。
   不要用 feat/T101-xxx 之类的名字——最后一段对不上，PR 合并就不会自动唤醒你。
2. 实现，边做边跑 `pytest p0/tests -q`
3. 对照该任务"验收标准"逐条自检（第三节）
4. 开 PR，标题 `T{编号} {任务标题}`，描述写：改了哪些文件、怎么验证、指标有无变化、已知限制
5. 更新 docs/PLAN.md：状态改 pr-open，看板填 PR 链接与 CI 结果
6. **判断能不能自己合**（见第十节）：符合自动合并条件就自己 squash merge，不符合才等我
7. 发完成消息（第五节）
8. 立即做下一个任务，不要等我回复
   **重要：框架不会给你发"PR 已合并"的事件。别再等唤醒了。**
   - 你的 PR 在 300 行以内（且是一个可独立合并的单元）→ 你自己合，合完直接做下一个
   - 超过 300 行 → **先按第十一节拆**，不要直接丢给人
   - 超过 300 行 → 发卡片后**用轮询自查**（见 10.2），合并了你就继续

【三、自检清单】（不过不许开 PR）
- `pytest p0/tests -q` 全绿；新功能有单测
- 规则类改动：12 份草稿的判定结论 diff 必须为空（除任务明确要求改判定）
- 视觉类（照片/设备标签/印章位置）无模型时，必须输出「未自动审核」，不得返回 pass，也不得静默跳过
- 没有提交 .env / API Key / 客户报告原文 / 临时文件
- 改动范围不超出任务声明的"涉及"；超了在 PR 里说明
- PR 描述贴了本地验证命令与输出摘要

【四、什么情况才停下来找我】
只有这五种，其余一律自己推进：
1. CI 红了，连续修 2 次仍红 —— 附失败日志关键片段
2. 需要业务/架构决策 —— 列选项 + 你的推荐 + 理由
3. PLAN.md 里 todo 全部完成 —— 发阶段汇总
4. 任务标记 blocked 且缺数据 —— 按第六节格式写清缺什么、找谁要
5. 阶段门禁指标不达标（T109/T110）—— 报当前指标 vs 目标，给出补齐方案，不许硬凑

不要因为"觉得有风险""想让我确认"就停。有风险写进 PR 描述，继续下一个。

【五、消息模板】
完成一个 PR：
  ✅ T102 表格单元格解析  [PR #35]
     改动：+380 −42，3 个文件
     自检：pytest 全绿（48 passed）；12 草稿判定 diff 为空
     指标：R02 在 12 份草稿上 12/12 判出均值空白（此前 9/12）
     下一步：T103 目录/书签/样式解析（已开始）

阻塞（缺数据）：
  ⛔ T105 三类模板字段映射 · blocked
     卡在：XG 变更报告无样例，无法验证模板识别
     需要：XG 报告 2–3 份（已记入 PLAN.md 第五节 D1）
     已做：BYD-odor 字段映射已提交，等样例后补 XG
     我先去做 T103，这条等你给数据

阶段汇总：
  🎉 阶段 1 完成（T101–T110）
     合并 PR：#35 #36 #38 #39
     门禁：12 草稿复现 POC ✅ / 16 变异 16/16 检出 ✅ / 0 误报 ✅
     指标：总体准确率 96.2%，召回 91.4%；编号/结论/日期/判定 100%
     未达项：T105 XG 模板（blocked，缺样例）
     建议进入阶段 2 前先补 D1/D3

【六、blocked 写法】
必须包含四要素，缺一不可：
  - 卡在哪个任务/哪条规则
  - 缺什么（具体到文件类型与数量）
  - 找谁要（业务/客户 IT/项目负责人）
  - 你还能做什么（是否可以绕开，绕开后验收标准怎么变）
写完后同步更新 PLAN.md 第五节的「数据需求」表。

【七、红线】
- 不许直接 push main，一律走 PR；但**符合第十节条件的小 PR 允许你自己 squash merge**（这是唯一例外）
- 不许改别人分支、不许 force push、不许用 `gh pr merge --admin` 绕过保护、不许绕过 CI 强合
- 不许删测试、skip 测试、写死返回值来"过"
- 不许造数据：没有任务单就用 12 草稿 + 4 记录做基线，不许伪造字段
- 不许改 PLAN.md 的任务定义和验收标准（不合理在 PR 里提，我改）
- 不许把客户报告原文、编号、VIN、联系人发给公网模型而未脱敏
- 视觉类没模型就标「未自动审核」，不许假装通过

【八、节奏】
- 一个任务做完不停顿，直接下一个
- 每 PR 发一条完成消息，不用等我回
- 每 3 个 PR 或每天结束发一次汇总：已完成 / 进行中 / 下一个 / 指标变化 / 阻塞
```

## 按 v1.2 补的两条硬约束

1. **门禁先于进度**。阶段 1 的 T109（回归）和 T110（指标）是门禁任务，不是"顺便做"。
   没有 12 草稿复现 + 16/16 变异 + 0 误报，就不算阶段 1 完成，agent 不得自己宣布进入阶段 2。
2. **12 份草稿 ≠ 12 份独立报告**。它们只是同一报告编号的 12 个模板变体。任何"准确率 92%"
   之类的结论，必须写清样本口径，不能拿模板变体冒充独立样本——这是 v1.1 踩过的坑。

## 九、卡片交互（2026-11-03 修订 v2）

### 9.1 卡片只做通知，没有「继续」按钮

每个 PR 开完后执行：

```bash
"/Users/liutongzhunew/Desktop/01云安公司资料/deepseek agent/bin/send-pr-card" \
  --task T104 --pr 41 --ci 通过 --summary "一句话改动" --next "T105 xxx"
```

卡片上只有**「暂停」「打回」**两个按钮——这两个是叫停，任何时候点都安全。

**没有「继续」**：继续由「合并 PR」自动触发，不需要任何人点按钮。

### 9.2 收到卡片操作怎么处理

文本形如：

```
T102 暂停（卡片操作）
T102 打回重做（卡片操作）
```

**按 action 处理，卡片里的任务编号一律忽略，以你当前手上的任务为准：**

| action | 动作 |
|---|---|
| `pause` | 停下手上的任务，把进度写进 PLAN.md，回一句「已暂停在 Txxx」 |
| `rework` | 当前 PR 标记需重做，PLAN.md 改回 `doing` 并写明原因，等我补充意见后重做 |

### 9.3 什么情况才发卡片

- **每个 PR 完成**：发一张通知卡（默认动作）
- **需要我决策**：可以在卡片里加选项按钮，但必须在正文写清「A / B 选哪个，各有什么取舍」
- 日常进度不要刷卡片；长解释写在 PR 描述里，卡片只放一句话摘要

### 9.4 注意

- 卡片是**我发的通知**，不是指令来源；我不点按钮，你也按 PLAN 继续往下走
- 旧卡片的按钮可能被我误点，所以按钮只保留「暂停 / 打回」这类安全操作
- 框架**不会**推送"PR 已合并"事件，别等唤醒；合并/继续的判断按第十节自己来做

## 十、目标模式（一个工单干到目标达成）

> **2026-11-04 v3**：给一个目标，你自己拆任务、做、验收，直到目标达成才回报。
> 不再按批次停下来等我。

### 10.1 为什么能这样跑（机制依据）

框架里工单会结束的唯一原因，是「工单自己绑定的 PR 全部合并」（`core/tickets.ts` 的 `threadClosed → followsDone → end`）。
而绑定只发生在**报告时传了 `pr_number`**（`app/tools/executor.ts:91` 的 `claimPull`）。

所以：**不传 `pr_number`，工单就不会被 PR 合并终结**，可以一直干到目标达成。

### 10.2 三条硬规则

1. **分支名**：`agent/T<编号>-<短描述>`，例如 `agent/T201-semantic-review`
   ⚠️ 最后一段**不要等于工单短名**（`DSH_SUPERAGENT_NAME`），否则会被自动绑定
2. **报进度时绝不传 `pr_number`**；PR 号写在 summary 文本里就行
3. 工单只在你报 `state=ready` 时结束——所以**只有目标达成才报 ready**

### 10.3 每轮做什么

```
读 docs/PLAN.md → 取第一个 todo
→ 建分支 agent/T<编号>-xxx → 实现 → 自检 → 开 PR
→ 等 CI 绿 → gh pr merge --squash --delete-branch
→ 更新 PLAN.md 看板（merged + PR 号）→ 取下一个
```

循环，直到 PLAN.md 里该目标下的任务全部 `merged`。

### 10.3a 开 PR 不等于交付（2026-11-06 新增）

**合进去才算。** 所以：

- **≤300 行且不碰敏感路径** → 开完 PR、等 CI 绿、**立刻自己合**，然后直接做下一个任务
- **>300 行** → 先按第十一节拆
- **拆不动 / 碰敏感路径** → 发卡片，然后按 §10.3c 等人合并

### 10.3b' 中途不要报 ready、不要发逐条消息（2026-11-06 新增）

**`state=ready` 只用于"目标达成"，中途一律用 `state=progress`（不触发消息）。**

反面案例（2026-11-06）：它每开一个 PR 就报一次 ready，飞书收到
「T303 收尾就绪：PR #68（125 行）」「T303 剩余部分已就绪：PR #66（295 行）」，
人看到就手动去合了——**这些本来都该它自己合**。结果变成"每个 PR 都要人点一下"，
和"少打扰"的目标完全相反。

正确做法：

- 每开一个 PR：**不报、不说**，自己合掉，继续下一个
- 目标达成：`state=ready` + `bin/send-summary` 发汇总
- 受阻或需要人合并：才发消息

### 10.3c 需要人合并时怎么等（关键：**不要结束回合**）

**框架不会给你推「PR 已合并」事件。** 2026-11-06 实测：人手动合完 PR，你不会自己醒；
外部脚本用 `requeue` 也叫不醒你（会被判成"这条消息已处理过"）。

所以**唯一的办法是你在同一轮里自己等**：

```bash
for i in $(seq 1 40); do
  s=$(gh pr view <PR号> --json state -q .state)
  case "$s" in
    MERGED) echo "merged"; break ;;
    CLOSED) echo "closed"; break ;;
  esac
  sleep 90
done
```

**这段循环必须在本轮内跑完**——不要报 `ready`、不要发消息、不要结束回合。
一旦结束回合，就没人能把你叫醒，任务会一直挂着。

- 循环结束是 `merged` → 更新 PLAN 看板，**立刻做下一个任务**
- 是 `closed` → 停下来问我
- 跑满 40 次（约 60 分钟）还是 `OPEN` → 发一句「PR #n 还在等你合并」，**然后再开一轮循环**继续等
- 等待期间**不要开新 PR**（会互相冲突），但可以读代码、写 PLAN、做准备

### 10.3b 结束前必须自己发汇总（重要）

报 `state=ready` **之前**，先执行：

```bash
bin/send-summary --title "目标达成：阶段 2" --body "..."
```

**不要依赖系统转达。** 2026-11-04 实测：它 12:52 报了 ready、汇总写得完整，但那条消息根本没发到飞书（relay 断了），人完全不知道活干完了。

### 10.4 什么情况才停

只有这些：

- 缺数据（样例/台账/正式报告）→ 在 PLAN.md 标 `blocked`，把它从本轮目标里剔除，**继续做剩下的**
- CI 红了且自修 2 次仍红 → 停下来报给我
- 需要产品/架构决策 → 停下来问
- 目标全部达成 → 跑回归（T109 那套）+ 更新指标，报 `state=ready` + 汇总

**不要因为"想确认一下""觉得有风险"停下来。** 有风险写进 PR 描述，继续下一个。

### 10.5 目标怎么给

我一次只给一个目标，例如：

```
目标：完成阶段 2（T201–T204）。达成标准：四块全部 merged，语义召回 ≥80%、误报 ≤15%，回归 16/16 且 0 误报。缺样例的任务标 blocked 跳过，其余必须做完再报 ready。
```

### 10.6 与「批次模型」的区别

| | 批次模型（v2，已废弃） | 目标模式（v3） |
|---|---|---|
| 工单生命周期 | 一批 PR 合完就结束 | 干到报 ready 才结束 |
| 你介入频次 | 每 3–5 个任务一次 | 只在阻塞或目标达成时 |
| PR 绑定 | 绑（会用 pr_number） | 不绑（绝不传 pr_number） |

## 十一、PR 拆分（2026-11-06 新增）

**单个 PR 目标 ≤ 300 行。超了就拆，不是丢给人。**

### 11.1 为什么

- 超过 300 行的 PR，人看不完，审查变成走过场，出问题是事后才发现
- 出问题难定位、难回滚
- 大 PR 生命周期长，容易和别人冲突

### 11.2 怎么拆

按**能独立合并的单元**拆，不按行数硬切：

- 一个 PR = 一件事，能单独跑测试、单独合并、单独回滚
- 典型拆法：接口/数据读取 → 核心实现 → 与主流程集成 → 文档

示例（T301 实际 1147 行，本应这样拆）：

| PR | 内容 | 规模 |
|---|---|---|
| 1 | 验收脚本 + 数据读取 | ~300 |
| 2 | 报告生成 + 指标计算 | ~300 |
| 3 | 与主流程集成 | ~300 |
| 4 | 文档 + PLAN 更新 | ~100 |

### 11.3 拆不动怎么办

**只有两种情况**才发卡片通知人：

1. 本质上是原子改动，拆开就是半成品（如一次性数据迁移、跨模块重构）
2. 触碰敏感路径：`deploy/`、`.env*`、`migrations/`、`*.pem`、密钥文件

通知时写明：**为什么拆不动、这次多少行、风险是什么**。不要只发一个数字。

### 11.4 开 PR 前自查

```bash
gh pr view <PR号> --json additions,deletions --jq '.additions + .deletions'
```

> 300 就回去拆，不要合并，也不要说"等人合并"。

## 十二、报结论前的验证义务（2026-11-06 新增）

**任何"环境 / 权限 / 配置"结论，必须附一次最小验证。没验证就不要写进汇报。**

### 12.1 为什么加这条

2026-11-06 实例：PR #16 合并失败，真实原因是**分支冲突**（`mergeable=CONFLICTING`，落后 main 110 个提交），
但汇报成了"这个部署没配置合并工具、机器人账户自己不能合并 PR"。
人差点去改部署设置——**排查方向被带偏，浪费的是人的时间**。

实际上机器人有 `push: true` 权限，同一账号合过 #56/#58/#59/#61，实测 `gh pr merge 2` 也成功。

### 12.2 先跑什么

| 你下的结论 | 必须先跑 |
|---|---|
| "没有权限" | `gh api repos/<owner>/<repo> --jq .permissions`、`gh api user --jq .login` |
| "网络不通" | `git ls-remote <url> HEAD`（HTTP 探测失败 ≠ git 不通） |
| "工具没装" | `command -v <tool> && <tool> --version` |
| "合并失败" | `gh pr view <号> --json mergeable,mergeStateStatus` |
| "配置没生效" | 把配置读回来贴出来，不要只看写入返回值 |

### 12.3 汇报写法

命令和输出一起写，例如：

```
#16 合并不了：mergeable=CONFLICTING（落后 main 110 个提交，需要 rebase 解决冲突）
验证：gh pr view 16 --json mergeable,mergeStateStatus → CONFLICTING / DIRTY
```

不要写"应该是权限问题""可能是配置没开"——**不确定就说不确定，并给出你验证过的部分**。

## 十三、飞书消息格式（2026-11-07）

**发给飞书的消息是给人看的，不是给工程师看的。** 技术细节写进 PR 描述和 docs/，不许堆在群里。

### 13.1 固定三段，最多 10 行

```
【结论】一句话说清做完了什么、结果如何
【要你决策】0–3 条，每条给选项；没有就写「暂无」
【详情】PR 链接 + 文档链接
```

### 13.2 技术细节去哪

| 内容 | 位置 |
|---|---|
| 改了哪些文件、函数、参数名 | PR 描述 |
| 实测数据、口径说明、局限 | docs/ |
| 失败重试、报错堆栈 | 不要发；除非需要人决策 |

### 13.3 反例（2026-11-07 实际发生）

> T403 去水印已按确认方案实现并合并（#91–#93）：文本层只删同页重复 ≥4 次的
> TO/OF/BY/AT 水印块，样例 33 页 132 组全删、正文与页眉标准号保留；扫描件走浅粉掩膜……

人看不懂 `TO/OF/BY/AT` 是什么，也不关心掩膜算法。应该写成：

```
【结论】水印处理做完了，33 页样例验证有效，正文没被误删
【要你决策】暂无
【详情】PR #91-93 · docs/t403-watermark-ocr.md
```

### 13.4 例外

**受阻待决策时可以长一些**，但必须把「我需要你做什么」放在第一行。

### 13.5 为什么

人如果看不懂消息，就得找人翻译一遍再回传——这个来回的成本比写消息时少写两行高得多。

### 12.4 判断「缺资源」之前，先查已知清单（2026-11-07 新增）

**在说"我需要 X 才能继续"之前，先确认三处：**

| 查什么 | 在哪 |
|---|---|
| P0 应用 / WeKnora 凭据 | `/opt/dsh-agent/.p0-secrets.env`（600，只有你能读） |
| 项目阶段、模型策略、数据策略 | `docs/project-context.md` |
| GitHub 权限 | `gh-agent` 已登录，不需要你自备 token |

**查完仍不确定**：发一条消息问人，一句话说清「缺什么、做什么用、卡住哪个任务」。
**不要自己停下来重试，也不要把"我认为缺 X"当成结论写进汇报。**

### 12.4b 同一操作失败 3 次，必须停

同一个命令 / 同一个接口连续失败 **3 次**，立刻停下来报告。
不要换参数硬试，不要换路径硬试，不要循环重试。

### 12.4c 两次真实事故（都发生在 2026-11）

**事故一（11-06，代价 9.5 小时）**
用错误的地址（`/api/v1` 应为 `/p0/api/v1`）和错误的账号（WeKnora 账号登录 P0 应用）反复重试，
session 里累计 348 次 `401`、344 次 `timeout`、190 次 `502`，一个 turn 跑了 60 多步。
正确凭据当时就在 `.p0-secrets.env` 里。

**事故二（11-07，代价一轮任务停滞）**
报 blocked，理由是"缺 GPU 访问"和"缺 DeepSeek API Key"：
- 语义审核耗时可以直接打 P0 的 `/api/v1/reports/audit`，**服务端自带 key**，不需要你自备
- GPU 是客户侧部署时的事，当时根本不需要

**共同点**：它对自己能拿到什么资源的判断，比实际情况悲观；遇到不确定就自己停下或硬试，
而不是问一句。
