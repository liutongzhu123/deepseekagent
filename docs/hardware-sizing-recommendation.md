# 模型与硬件选型建议

> 版本：v1.2 ｜ 日期：2026-11-07
> 面向：中汽报告审核 / 标准问答项目的选型与采购决策
> 数据口径：正文数字均为实测；推算值单独标注；未实测的项写“未实测”，不用估算冒充实测。

## 0. 结论摘要

- **现阶段不需要买 GPU。** 公网 DeepSeek + 现有 CPU 服务器已满足当前目标：现网检索 P95 **299.9 ms**（目标 < 8 s），44 页扫描件 OCR 约 **99 s**。
- **只有两类需求建议上 GPU**：语义审核必须完全本地化且要可接受的交互速度，或确定要启用 rerank。两者都必须先在 GPU 上复测，不能把 CPU 结果直接外推。
- **rerank 当前不可用**：CPU 上 P95 **54.6 s**（空闲主机；带负载实测 126.4 s）；把候选缩到 15/10 个仍为 P95 **40.1 s / 25.5 s**（带负载），且 10/15 是离线回放、当前 WeKnora 候选池固定 50，不能直接上线。**需 GPU 或缩小候选池后重测。**

## 1. 先回答：要不要买 GPU？

| 你的场景 | 建议 | 关键依据 |
|---|---|---|
| 试点/受控上线，文本语义可走公网（脱敏后） | **不买** | 检索 P95 299.9 ms；OCR 2.25 s/页；公网文本调用 P95 约 1.2 s（改写场景） |
| 客户要求语义审核/图像理解完全本地化 | **要买**，或接受明显变慢 | 本地 CPU 单次短文本 P50 24.1 s / P95 26.0 s；图像约 62 s/张（qwen2.5:3b） |
| 想用 rerank 提升检索质量 | **先买/租 GPU 复测，再决定** | CPU rerank P95 54.6 s（空闲；带负载 126.4 s）；10/15 候选仍 >2 s（带负载），且候选池降不下来 |
| 只做扫描件 OCR/解析，语义仍走公网 | **不买** | OCR 在 CPU 上 2.25 s/页；瓶颈是单实例并发，不是算力 |

**一句话**：试点期不买；只有“语义审核必须本地化且要可接受的交互速度”或“确定要上 rerank”时才进入 GPU 采购，且采购前先做 GPU 复测。

## 2. 三档方案对比

| 档位 | 组成 | 数据是否出网 |
|---|---|---|
| **A 公网 API** | 公网 DeepSeek 做语义审核/查询改写；WeKnora 做检索（hybrid，不开 rerank）；本地 RapidOCR | 文本出网（需脱敏）；扫描件 OCR 在本地 |
| **B 本地小模型 CPU** | 本地 WeKnora 检索 + 本地 Ollama 小模型（如 qwen2.5vl）做语义审核/图像理解；本地 RapidOCR | 不出网 |
| **C 本地 + GPU** | 在 B 的基础上，为 reranker 与本地视觉/语义模型加 GPU；检索仍走 WeKnora | 不出网 |

### 2.1 时延对比

| 指标 | A 公网 API | B 本地小模型 CPU | C 本地 + GPU |
|---|---|---|---|
| 检索首字（无 rerank） | 现网 P0：P50 271.4 / P95 **299.9 ms** | 直连 hybrid：P50 255.7 / P95 **469.5 ms** | 未实测；无 rerank 时检索段与 B 相同 |
| 检索完整响应（无 rerank） | 现网 P0：P50 271.8 / P95 300.6 ms | 直连 hybrid：P50 2.37 / P95 **3.43 s** | 未实测 |
| 检索 + rerank | 不默认开启；CPU 实测 P95 **54.6 s**（空闲；带负载 126.4 s），不可用 | 50 候选 P95 **54.6 s**（空闲；带负载 126.4 s）；15/10 候选 P95 **40.1 / 25.5 s**（带负载） | 未实测；门槛：15 候选 P95 ≤ 2 s |
| 语义审核 | 未单独计时；同模型单次文本调用 P50 0.83 / P95 **1.16 s**（改写场景，15 次） | 约 **5.5 tok/s**；图像约 **62 s/张**；单次短文本 P50 **24.1 s** / P95 **26.0 s**（qwen2.5:3b） | 未实测 |
| OCR | **2.25–2.26 s/页**（44 页约 99 s，4 vCPU） | 同左 | 未实测；OCR 当前走 CPU，GPU 收益未验证 |

> 表中“首字”指从请求到首个可见内容；“完整响应”指到答案 JSON 返回。现网 P0 是同步 JSON 接口，首字与完整响应几乎相同。
>
> **术语**：**hybrid（混合检索）** = 关键词与向量检索组合，不含重排序；**rerank（重排序）** = 召回后用模型对候选段落重新打分，目的是提高引用准确性，代价是额外算力；**P95** = 95% 的请求不超过该值；**tok/s** = 每秒生成的 token 数，越大越快。

### 2.2 硬件配置与适用场景

| 档位 | 硬件配置要求（实测/最低） | 适用场景 | 不适用 / 主要限制 |
|---|---|---|---|
| **A 公网 API** | 4 vCPU / 15.6 GB，无 GPU；公网出口 + DeepSeek API 账号；OCR 单实例 | 试点、内部用户、低并发；文本可脱敏出网 | 依赖公网与合规；语义审核未单独计时；rerank 不可用 |
| **B 本地小模型 CPU** | 8 vCPU（reranker/WeKnora 主机），无 GPU；OCR 侧 4 vCPU；本地 Ollama 模型 | 数据不出内网、低并发、只用 hybrid 检索 | 单次短文本约 24 s、图像 62 s/张，吞吐不足；rerank 不可用；语义审核会明显慢 |
| **C 本地 + GPU** | 在 B 基础上加 1 张 GPU；型号/显存按 bge-reranker-v2-m3 与 qwen2.5vl 实测确定（本轮未实测） | 本地语义审核、要开 rerank、并发较高 | GPU 收益未实测；需先改 WeKnora 候选池；成本最高 |

## 3. 逐档说明

### 3.1 A 档：公网 API（当前推荐用于试点）

**实测延迟**：现网 P0 语义检索路径（不经 rerank）5 题 × 4 次 = 20 次/组，命中 100%，P50 **271.4 ms** / P95 **299.9 ms**；确定性关键词基线 P50 **31.1 ms** / P95 **34.2 ms**。直连 WeKnora hybrid 检索首字 P50 **255.7 ms** / P95 **469.5 ms**，完整响应 P50 2.37 s / P95 3.43 s。

**语义审核**：走公网 DeepSeek。本次没有单独给“一次语义审核”计时；同模型同量级的单次文本调用实测 P50 **832.5 ms** / P95 **1163.1 ms**（改写微基准，15 次），可作为量级参考，不作为语义审核的正式指标。

**OCR**：本地 RapidOCR，44 页扫描件端到端约 **99 s**，折合 **2.25–2.26 s/页**；4 vCPU 下单实例 OCR 并发上限为 1，扫描期间其他接口会排队。

**适合**：当前试点、内部用户、低并发；客户能接受文本脱敏后出网。

**前提**：按已确认的合规口径脱敏，不把客户报告原文、VIN、联系人等发到公网模型。

### 3.2 B 档：本地小模型 CPU（数据不出网的低配版）

**可切换性已验证**：语义审核与 WeKnora 视觉模型都可在不改代码的情况下切到本地 Ollama，属于配置级切换；但本轮没有真实 Ollama 模型 + 真实报告的效果验收。

**实测吞吐**：本地 CPU 约 **5.5 tok/s**，图像约 **62 s/张**。这意味着本地语义审核在小批量、低频场景可用，但交互式使用会明显等待。2026-11-07 补测（qwen2.5:3b，5 条合成短文本 × 2 次，带负载）：单次审核 P50 **24.1 s** / P95 **26.0 s**；真实报告更长，耗时会更高，详见 `docs/eval-p1-semantic-latency.md`。

**检索**：本地 hybrid 检索首字 P50 255.7 ms / P95 469.5 ms，和公网档同一量级；rerank 在 CPU 上不可用（见第 4 节）。

**OCR**：与 A 档相同，2.25–2.26 s/页；瓶颈是单实例并发，不是识别速度本身。

**适合**：客户明确要求数据不出内网、并发低、语义审核可以等待结果。

**不适合**：交互式语义审核、开启 rerank、批量扫描件并发处理。

### 3.3 C 档：本地 + GPU（能力上限，但尚未实测）

本轮**没有 GPU 实测数据**，以下是采购前必须验证的目标，不是已实现结果：

1. **rerank**：15 个候选要压到 P95 ≤ 2 s，每候选需 ≤ **0.133 s**；当前 CPU 空闲约 1.04 s/候选、本次负载下约 2.49–2.53 s/候选，差 5–19 倍。GPU 是最主要的提速手段，但具体能到多少必须实测。
2. **语义审核/图像理解**：CPU 上约 5.5 tok/s、图像约 62 s/张；GPU 预期能提升，但本轮没有数据，不能承诺倍数。
3. **OCR**：当前 CPU 已能到 2.25 s/页，上 GPU 的收益未验证；如果只是 OCR 并发问题，优先做任务队列/多实例，而不是买 GPU。

**适合**：客户要求语义审核完全本地化且要交互速度；或确定要上 rerank 并愿意先做 GPU 试点。

**前提**：先让 WeKnora 的 rerank 候选池可配置（当前固定 50），再用 GPU 复测 15 候选 P95 与 5 题命中质量，最后才决定是否默认开启 rerank。

## 4. rerank 单独说明

### 4.1 当前 CPU 上不可用

直连 WeKnora 的 `knowledge-search`（开启 rerank，50 个候选）5 题 × 2 次 = 10 次/组，空闲主机实测：

- 首字 P50 **52.1 s** / P95 **54.6 s**；完整响应 P95 **55.2 s**。
- 比 hybrid 检索首字 255.7 ms 慢约 **204 倍**，远高于 T401 的 **P95 < 8 s** 目标。
- 现有问答超时默认 60 s，P95 54.6 s 只剩约 5.4 s 余量；在线开启 rerank 有超时/502 风险。

**当前 CPU 上 P95 54.6 s（空闲主机；带负载 126.4 s）不可用；需 GPU 或缩小候选池后重测。**

### 4.2 缩小候选池也不够

同一台 CPU reranker 上的实测（主机负载 2.5–3.5）：

| 候选数 | 样本 | P50 | P95 | 每候选 P50 |
|---:|---:|---:|---:|---:|
| 50 | 5 | 126.4 s | 134.8 s | 2.53 s |
| 15 | 15 | **37.8 s** | **40.1 s** | 2.52 s |
| 10 | 15 | **24.9 s** | **25.5 s** | 2.49 s |

- 15/10 候选仍比 2 s 门槛高 **12–19 倍**。
- 即使按 T401 空闲主机 50 候选 52.1 s 的每候选成本（约 1.04 s）折算，15 候选仍需约 **15.6 s**、10 候选约 **10.4 s**，仍 > 2 s；减少候选数量本身达不到 2 s。
- 只有 1–2 个候选理论上可能压到 2 s 内，但候选太少，rerank 已失去排序意义。

### 4.3 重要口径：10/15 是离线回放，不是可直接上线的配置

- 本报告的 10/15 是**离线回放**：对同一 50 个候选的前 N 个调用 reranker，用来验证“即使能降候选，模型成本是否够低”。
- WeKnora 0.9.0 把 rerank 候选池硬编码为 **50**（`max(top_k, 50)`），请求里的候选数/结果数参数无法把实际打分池降到 10/15。要端到端降候选，必须改 WeKnora 并重新部署，不在本轮范围。
- 因此，10/15 的数字只能用于判断成本趋势，**不能当作现有系统可配置的在线路径**。

### 4.4 主机负载影响

- T401 的 50 候选 P50 52.1 s / P95 54.6 s 是**空闲主机**的结果（与 T405 同一台 8 vCPU、无 GPU 的 reranker 主机）。
- T405 复测时主机有其他并发负载（load average 2.5–3.5），50 候选实测 P50 **126.4 s** / P95 **134.8 s**，明显高于空闲值。
- 15/10 候选是在**当前负载**下实测的；空闲时按每候选 1.04 s 折算仍约 15.6 s / 10.4 s，**结论方向不变**。本文所有 rerank 绝对值都受主机负载影响，引用时需带上口径。

### 4.5 什么条件下才重新评估 rerank

1. WeKnora 提供可配置候选池（10/15），部署后复跑端到端计时；
2. reranker 改用 GPU 或更小/量化模型，使 15 候选 P95 ≤ 2 s（每候选 ≤ 0.133 s）；
3. 满足 1 + 2 后，用同一组 5 题对比 hybrid 与 rerank 的命中率、引用准确率、拒答率，再决定是否默认开启。

在此之前，问答默认走 hybrid（无 rerank）；rerank 只作为显式实验开关，不进入生产默认路径。

## 5. 场景化建议

| 客户场景 | 推荐档位 | 说明 |
|---|---|---|
| 近期试点/受控上线，追求稳定与低门槛 | **A** | 现有服务器即可；检索 P95 0.3 s；OCR 2.25 s/页；文本脱敏后出网 |
| 要求数据完全不出内网，但并发很低 | **B** | 检索与 OCR 可用；语义审核单次短文本约 24 s、图像约 62 s/张，需接受等待 |
| 要求本地化且语义审核要交互速度 | **C，先做 GPU 试点** | 本地 CPU 单次已约 24 s（短文本）；先复测 GPU 上的语义审核单次耗时与 rerank 15 候选 P95 |
| 想提升检索准确率、要开 rerank | **C + 改 WeKnora 候选池** | CPU 上不可用；10/15 候选仍 >2 s（带负载）；候选池当前固定 50 |
| 只关心扫描件 OCR/解析 | **A 或 B，不买 GPU** | OCR 2.25 s/页；优先解决单实例并发（队列/多实例），GPU 收益未验证 |

**不建议**：
- 在 CPU 上开启 rerank 作为在线默认路径（空闲 54.6 s、带负载 126.4 s，有超时风险）；
- 仅为提升 hybrid 检索速度买 GPU（检索本身 P95 0.3 s，不是瓶颈）；
- 用 10/15 候选的离线回放数字当作现有系统可上线的配置。

**口径说明**

- 检索与 rerank 的数字来自 `docs/eval-p1-*.md`；本地模型与 OCR 的耗时不在 eval-p1 文档中，引用同批实测报告，未做重算。
- T403 的水印对比记录的是 OCR 行数/字符数变化，**没有记录耗时**；本文 OCR 耗时取自上述 44 页扫描件实测，不用 T403 的行数推算时间。
- 公网 API（A 档）的语义审核“单次耗时”仍未单独计时；正文引用的 0.83 s / 1.16 s 是改写场景的同模型调用，只作量级参考。
- 本地 CPU 的 24.1 s / 26.0 s 是 qwen2.5:3b 在 124–139 字合成短文本上的实测，带负载、无 GPU；真实报告更长、现场模型不同，不能直接外推为客户 SLA。
- 10/15 候选是离线回放，不是现有系统的可配置在线路径；50 候选的 52.1 s / 54.6 s 是空闲主机结果，126.4 s / 134.8 s 是带负载结果。摘要与表格中的 54.6 s 均指空闲主机，对外引用时需同时说明 126.4 s 的带负载值。
- GPU、GPU 上的语义审核、GPU 上的 OCR 均**未实测**；本文没有给出 GPU 的提速倍数或具体型号/显存要求。
- 评测问题集是 5 题，语义用例是 44 条合成用例，12 份草稿是同一报告的模板变体；它们只作链路/口径基线，不是客户金标准，不能替代 20–30 份正式报告验收。
